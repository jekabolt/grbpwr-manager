# Saved native Join on UpdateTechCard

The Draft geometry fixture at frontend commit `522edd49e` supplies one reviewed cut-boundary Join across two separate saved pieces in one material and grade. The ordinary worker reproduces its output in R12 and R2000. At backend commit `80d10962d`, the production gateway accepts an ordinary document or the sparse name-change command. Its request descriptor has no Join field. The local gateway test observes HTTP 400 before a Join reaches the RPC. The private store preflight in this patch has no caller from a write command.

## Request for the existing endpoint

Extend `UpdateTechCardRequest` on `POST /api/admin/tech-card/update` with a single optional message `guarded_piece_join` (field 7 is available on this pin). Submit only the existing card ID, expected lock version and this message. Reject requests that include `tech_card`, guarded rename, save session ID, or caller-provided snapshot reason. An older permissive gateway will discard the unknown command and produce an empty document, which the ordinary converter rejects.

The message needs these bindings.

| Field | Meaning |
| --- | --- |
| Saved sheet | Existing row scope, stable pattern line key, saved row revision, human version, URL, exact byte length and SHA-256. Card and lock come from the outer request. |
| Assembly before review | Assembly revision and complete-source SHA returned by the existing complete saved-assembly read. |
| Two ordered source selections | For the fixed and translated piece, its exact line key, complete list of scoped alias spellings, native identity, grade token/ID/rank, source curve ID and two directed original vertex IDs. Include the confirmed translation in the writer’s exact unit. |
| Reviewed output | Newly minted piece line key, new native identity and reviewed scoped alias. Ordinary UploadPattern result URL/filename/byte count plus the SHA of the final Wizard bytes. |

Keep the normal Wizard's explicit **New piece** answer, mint its line key once, and seal that exact review before manual Apply. At the moment, the frontend geometry preparation returns a detachable result. It has no durable dual-source marker in the ordinary output manifest, and cannot serve as a save receipt. The ordinary writer must retain and re-open the source selections in the reviewed file before this command can be issued. The stored marker binds the previous byte SHA, two source identities, native intervals and confirmed transform. Keep the output SHA in the guarded request, outside the file that it hashes.

Use the existing UploadPattern followed by exactly one UpdateTechCard, only after operator confirmation. UploadPattern returns a URL, name, and byte length. The ordinary DTO accepts a syntactically valid supplied SHA. For guarded replacement, resolve the configured object host with `bucket.ManagedObjectKeyFromURL`, check its pattern-path binding and open the immutable object using `GetManagedObject`. Compare observed count and SHA with the review and validate the file’s dual-source/output record. Reading bytes via a supplied external URL or validating just the reported SHA cannot establish this binding. The verified original/child geometry remains owned by the normal native reader. The reviewed-file marker/verification contract and its ordinary fresh re-import are pending.

## Transaction

1. Reuse the server-built document path from guarded rename. Resolve the ordinary authenticated user, current card, storage ownership and review facts. Limit the proposed replacement to the exact sheet, two source groups and independent result. The server generates the snapshot reason.
2. Enter `Store.UpdateTechCardTx`. After the existing card-row `FOR UPDATE` and expected lock check, call `readJoinRetirementUnderLock` on its repository **before** any destructive document diffs or snapshots. The helper verifies the current complete-source binding, rows, alias groups, Assembly references and raw persisted seam sides. The first profile refuses attachments/areas/markers, recipe-linked inputs, uncertain bindings and collateral seam/fold/topstitch changes in the replaced cloth scope. Production piece deletion otherwise explicitly removes recipe rows, areas and folds. The complete-source API includes only operation-owned seams in its digest. An unowned rejected seam or label POSE still owns its anchors.
3. Build or validate the submitted delta against that locked state. Keep the two source line keys out of the new active piece set, remove exactly the verified alias groups, retain every unrelated binding and add the separate reviewed key/alias. Replace the **same** pattern line with the verified uploaded file. Check uniqueness of result keys and names across the current document. Keep all other payload sections on their established carry path.
4. Before commit, fresh-read through the same transaction. Use the isolated `verifyJoinLineDelta` predicate for the exact resulting source/child line keys, numeric IDs, and every alias row. Check the ordinary one-step document lock, the same pattern line with the new bytes and expected revision transition, disappearance of both source lines and aliases, and a unique new result line and scoped alias. Compare unrelated logical rows and all durable references, including stale/fresh state. Allow only server-owned revision, history, journal and timestamp transitions that the existing document writer actually makes. Retain the old file through its normal history and snapshot. Any mismatch aborts this transaction.
5. After the response, require a fresh GetTechCard plus ordinary saved-row native reread of the new bytes. An ambiguous response requires reading the current exact state before offering manual retry. A deletion, fallback match by name, second form write, or retry against a new lock cannot repair a failed guard.

## Native lineage checkpoint

The server can now read the two immutable DXF files through the same managed-object store that holds ordinary pattern uploads. It checks the configured bucket host and base folder, the exact size and SHA-256 and the compressed writer manifest. The verifier walks physical block entities and insertions in both files. It reconstructs the two source curve IDs and directed endpoint IDs from the stored file identity, occurrence, block, entity and edge. It verifies the reviewed child against the registered source edges, directed grain, signed cut holes, drills, Darts, text and point marks.

The initial profile admits one size and two zero-allowance rectangles with their entire right and left edges selected. Coordinates must fit the writer's six-decimal representation within ±999.999999 mm. Holes must be strictly interior, disjoint clockwise rectangles. Authored internal paths must be three-point open Darts. A marker must agree with its physical entity and rank. The two original native names and the result name must be distinct. The managed source holds exactly these two pieces, and the reviewed file holds the single result. Legacy imports continue through their current owners.

The detached Ed25519 envelope includes the original saved row, Assembly revision and complete-source digest, ordered input line keys, fresh result key, both assets, native paths, selection and exact translation. The complete-file digests are external to the DXF to avoid a circular hash. Signing and matching take a server-owned document checker. The store checker derives each alias group from the locked card and requires its real BOM line and material scope before entering the retirement predicate. Verifying a previously signed envelope requires fresh expected inputs, both managed objects and another successful document check.

The writer fixtures in `internal/patternjoin/testdata` are the outputs of the existing frontend Join preparation and ordinary Patterns Wizard on commit `522edd49e`, captured using canonical row, BOM and piece keys. Each intent is the source edge selection produced by that frontend. The source and child drawing each pass their normal writer gate. The backend tests run the production bucket adapter against a loopback S3 response, verify each dialect and exercise the signer in the ordinary document transaction against a controlled SQL driver. The checkpoint returns before the writer changes any rows.

The next integration must construct the requested result projection from the locked card and ordinary pattern row update, check the exact post-write delta in that same transaction, and qualify the sparse field 7 command against the real gateway and a disposable MySQL database. A private signing key must remain server-owned. If both signature operations stay inside one synchronous transaction, use an ephemeral key there and return only the ordinary save response. Durable external verification would instead require a dedicated configured key and a durable signed-envelope channel. The checkpoint has no RPC, no deployed signing key and no operator control.
