# Осиротевшие объекты схемы, ждущие отдельной миграции на снос

Здесь перечислено то, что живой код УЖЕ не читает и не пишет, но что осталось в схеме намеренно —
чтобы не закрывать откат на предыдущий бинарь в момент выкладки. Платформа при провале health-check
откатывается на прежний образ молча (`readyz` при этом врёт), поэтому дроп колонки, которую старый
бинарь ещё именует в INSERT/UPDATE, обязан ехать ОТДЕЛЬНОЙ волной — после того, как прод отработал
на новом бинаре.

Список не декоративный: мёртвая колонка, которую никто не сносит, однажды находится следующим
писателем и начинает заполняться — и тогда один факт хранится в двух местах, расходящихся молча.

## `task.assignee` + индекс `idx_task_assignee`

- **Осиротели**: волной мультиасайна (`0337_task_assignees.sql`, 2026-08-25). Исполнители переехали
  в `task_assignee(task_id, username, display_order)`; бэкфилл 0337 перенёс единственного
  исполнителя каждой карточки.
- **Кто читает/пишет сегодня**: НИКТО. `internal/store/task/task.go` больше не именует колонку ни в
  INSERT, ни в UPDATE, ни в предикате `ListTasks`; `internal/store/task/files.go` не берёт её в
  проекцию карточки файла. Поля `Assignee` нет ни в `entity.TaskInsert`, ни в
  `entity.LibraryFileTask`. Проверяется одной командой:
  `rg -n "\bassignee\b" internal/store/task internal/entity/task.go` — вхождений колонки быть не
  должно (`assignees` — это уже новая таблица).
- **Почему не дропнута сразу**: до-волновой бинарь именует `assignee` в INSERT/UPDATE задач, и после
  дропа его запись в `task` падала бы. Окно риска — «миграции применились, а деплой не прошёл
  health-check и платформа откатила бинарь». Последствие ограничено записью карточек внутреннего
  канбана, но ночью, без владельца, оно недопустимо.
- **Что сделать потом**: одна миграция, один ALTER под гвардом по `information_schema`
  (`PREPARE`/`EXECUTE`/`DEALLOCATE` по одному оператору на строку — прод ходит без
  `multiStatements`):

  ```sql
  ALTER TABLE task DROP INDEX idx_task_assignee, DROP COLUMN assignee
  ```

  ALTER по таблице в сотни строк — секунды, пятиминутный лимит миграций не задевается. Ретроактивных
  CHECK нет. Down-ветка возвращает `assignee VARCHAR(255) NOT NULL DEFAULT ''` и индекс; при желании
  добивается первым исполнителем из `task_assignee` (`display_order = 0`).
- **Когда**: после того как прод отработает на бинаре волны мультиасайна, то есть откат на
  до-волновой образ перестанет быть сценарием.
- **Первоисточник решения**: `tmp/plans/ux-wave-0825/10-tasks-backend-plan.md`, раздел «Риски», п.1
  («если исполнителю нужен нулевой риск — дроп можно отложить, всё остальное от этого не зависит;
  но тогда в волне обязана остаться заметка на снос»).

## `TaskInsert.assignee` (поле 3 провода) и `LibraryFileTask.assignee` (поле 4)

Это не схема, а контракт, но живёт по тому же правилу и снимается той же следующей волной.

- **Осиротели**: там же. На проводе оставлены `deprecated`-алиасами на один релиз: на входе читаются
  только при пустом `assignees`, на выходе равны `assignees[0]`.
- **Почему не сняты сразу**: admin-гейтвей разбирает JSON с `DiscardUnknown: false`
  (`internal/api/http/http.go`), поэтому `reserved` на живом поле превратил бы каждое сохранение
  карточки из ОТКРЫТОЙ старой вкладки админки в 400.
- **Что сделать потом**: снять по процедуре инвентаря retired-полей (комментарий к
  `newAdminJSONMarshaler`, `internal/api/http/http.go`) — `reserved 3;` / `reserved 4;` плюс
  `reserved "assignee";`.

## Снос версий листа (0353) — НЕ отложенный дроп, а исполненный

**Это единственный раздел файла, который НИЧЕГО не ждёт.** Остальные разделы перечисляют
осиротевшие объекты, чей дроп отложен ради отката на предыдущий бинарь; здесь дроп уже написан и
едет вместе с кодом, потому что цена отката названа и принята владельцем.

- **Что снесено**: `design_sheet_issue`, `design_sheet_version_callout`,
  `design_sheet_version_plate`, `design_sheet_version` — вся четвёрка 0342, вместе с уже
  выпущенными подписанными листами, их content_hash и журналом выпуска. Необратимо и намеренно:
  «PRINT — MINTS V1 вообще этот функционал не нужен как и VERSIONS… Снести целиком, включая
  бэкенд».
- **Почему дроп НЕ отложен волной, в отличие от `task.assignee`**. Правило отсрочки защищает
  откат на до-волновой бинарь, который ещё ИМЕНУЕТ колонку в INSERT/UPDATE. Здесь защищать нечего
  в обе стороны: до-волновой бинарь пишет эти таблицы только внутри `MintDesignSheetVersion` и
  `RecordDesignSheetIssue`, а обе ручки сняты с провода этой же волной — то есть в откаченном
  бинаре писать в них уже некому, кроме отката САМОГО ПРОВОДА, которого не будет.
- **И наоборот, откладывать было бы вредно.** Две колонки держали `media(id)` через
  `ON DELETE RESTRICT`. Снять код, оставив таблицы, значит оставить файлы неудаляемыми навсегда,
  причём БЕЗ живого читателя, который объяснил бы человеку, кто их держит: `GetMediaUsage` теряет
  эти источники вместе с кодом. Дроп таблиц — единственное, что снимает пин.
- **Порядок**: дети перед родителем; три входящих FK смотрят на `design_sheet_version`, и
  снесённый первым родитель даёт 1217. Подробности — в шапке самого файла.

**Бронь — это не вежливость, а единственный работающий канал координации между параллельными
сессиями.** `sql-migrate` держит Id = ИМЯ ФАЙЛА, поэтому номер, взятый вторым файлом, становится
дублем НАВСЕГДА: переименовать уже применённый файл нельзя (это новый Id и повторное применение
DDL), а разойтись потом можно только ручной правкой `gorp_migrations` на бете и на проде.
Разъезд ловит красный тест `internal/store/migrationlint/numbering_test.go` — но он ловит его
у того, кто добавил файл вторым, а не у того, кто занял номер первым.

**Окно перенумерации открыто до первого деплоя беты этой волной.** Пока номера не применены,
весь блок двигается свободно; после — никогда. Поэтому непосредственно перед пушем:
`git fetch && git rebase origin/master && go test ./internal/store/migrationlint/...`.

# История: дыра 0336 закрыта, номер занят законно

Раздел исторический — предупреждать больше не о чем, но приём, которым это кончилось, нормативен.

**Что было.** Волна мультиасайна взяла номера 0337–0339, хотя на `origin/beta` последней миграцией
была 0335. Пропуск не был опечаткой: `0336_techcard_archive_import.sql` уже лежал в тогда ещё
НЕСЛИТОЙ ветке `feat/techcard-zip`, и занять этот номер вторым файлом значило получить два разных
файла с одним Id — состояние, из которого нет выхода без ручной правки `gorp_migrations`.

**Чем кончилось.** Ветка импорта архива влилась; `0336_techcard_archive_import.sql` лежит и на
`origin/master`, и на `origin/beta`. Номер 0336 занят законно и единственным файлом, дыры в
нумерации больше нет. Переименовывать его не надо и НЕЛЬЗЯ.

## Почему отставшая миграция всё-таки применяется — и почему её нельзя переименовывать

`sql-migrate` не просто идёт «дальше последнего применённого»: перед этим он собирает отставшие.
`planMigrationCommon` (migrate.go:620-622) зовёт `ToCatchup` с комментарием «Add missing migrations
up to the last run migration. This can happen for example when merges happened», а сам `ToCatchup`
(migrate.go:746-765) берёт каждую миграцию, которой нет в `gorp_migrations` и которая
`migration.Less(lastRun)`. Ровно наш случай.

**Замерено, а не выведено** (2026-08-26, одноразовый MySQL 8, чистая цепочка 0001→0339, затем
подложен файл с номером 0336):

```
OK: applied 1 migrations (staged 335) in 75.3ms
probe_table_exists = 1
0335_bom_kind_spare_kit_bag.sql   2026-08-25 22:10:12
0336_catchup_probe.sql            2026-08-25 22:10:22   <- отставшая, применилась ПОСЛЕ 0339
0337_task_assignees.sql           2026-08-25 22:10:12
0339_task_comment_author.sql      2026-08-25 22:10:13
```

Переименование, наоборот, ОПАСНО: sql-migrate ведёт учёт по полному имени файла, поэтому
переименованный файл — это НОВЫЙ Id, то есть повторное применение уже применённого DDL и
заклиненный старт (см. заметку `sql-migrate-renumber-orphan` и шапку 0334). Правило живо и
относится к любой будущей ветке, которая уедет в параллель, — не только к 0336.

## Что действительно не гарантируется — ПОРЯДОК, а не факт применения

Отставшая миграция ложится **после** старших номеров, а не между своими соседями. Значит:

- отставшая миграция не имеет права ЧИТАТЬ объекты, заводимые старшими номерами, и наоборот;
- если такая зависимость всё-таки нужна — её решает не номер, а гвард по `information_schema`
  внутри самого файла (он и так обязателен по правилу идемпотентности).

Прецедент в этом же дереве описан прямо в шапке `0334_operation_bom_qty.sql`: «НОМЕР ПРИМЕНИТСЯ ВНЕ
ЧИСЛОВОГО ПОРЯДКА, И ЭТО НЕ ОШИБКА… Безопасно по построению: файл трогает СВОЮ таблицу… и ни одного
объекта, заводимого ими, не читает».

Волна 0337–0339 этому правилу удовлетворяла с обеих сторон (только `task`, `task_assignee`,
`task_link`, `task_comment` против собственных таблиц импорта архива), и волна 0340–0347 обязана
удовлетворять ему так же: новые таблицы полосы DESIGN ссылаются только на `tech_card` и `media`,
которые старше всех номеров волны.
